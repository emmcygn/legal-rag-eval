# results/

Committed evidence. The README's generated tables, `docs/external_evals.md` and the
baseline-vs-fixed comparison are all rendered from these files, so a reader can check any
published number against the run that produced it rather than taking it on trust.

Ad-hoc runs land in `results/` itself with the CLI's default filenames and are **not**
committed (see `.gitignore`), so running a benchmark locally never overwrites the evidence
behind a published table. Only the build-named subdirectories and `external/` are tracked.

## What is here

Every run below was committed in harness commit
[`7fd1cce`](https://github.com/emmcygn/legal-rag-eval/commit/7fd1cce) ("Harness v2", PR #3).
LexiChunk version and commit are read back out of each file, not from memory.

| File | Size | What it is | Regenerate |
|---|---:|---|---|
| `full_benchmark.json` | 1.9 MB | As above, against 0.8.0b1. | `python -m legal_rag_eval benchmark-embed --json --seed 0 --models all-MiniLM-L6-v2,bge-base-en-v1.5 --output-dir results/lexichunk_baseline` |
| `structural_benchmark.json` | 1.5 MB | As above, against 0.8.0b1. | `python -m legal_rag_eval benchmark-structural --json --seed 0 --output-dir results/lexichunk_baseline` |
| `evidence_benchmark.json` | 86 KB | As above, against 0.8.0b1. | `python -m legal_rag_eval benchmark --output results/lexichunk_baseline/evidence_benchmark.json` |

Reproducing these needs LexiChunk 0.8.0b1 installed in place of the released one, which
`pyproject.toml`'s `lexichunk>=0.9.0,<0.10` will not give you. Install the checkout **last**
and record the commit yourself, because a directory install carries no VCS metadata:

```bash
pip install -e ".[dev,embeddings]"
pip install -e /path/to/lexichunk          # must come last
LEGAL_RAG_EVAL_LEXICHUNK_COMMIT=$(git -C /path/to/lexichunk rev-parse --short HEAD) \
  python -m legal_rag_eval benchmark-embed --json --seed 0 \
    --models all-MiniLM-L6-v2,bge-base-en-v1.5 --output-dir results/lexichunk_baseline
```

`make compare-builds` renders the two `full_benchmark.json` files side by side.

## Reproducibility check

`make benchmark-structural` against the released LexiChunk wheel from PyPI reproduces
`lexichunk_fixed/structural_benchmark.json` exactly: all 30 metric rows (6 strategies x
5 documents) match to the last floating-point bit. So does `make benchmark` against
`lexichunk_fixed/evidence_benchmark.json`, on all three strategy aggregates.

This was checked against **both** releases the dependency range admits, 0.9.0 and 0.9.1,
so `lexichunk>=0.9.0,<0.10` does not silently move a published number. Anyone widening
that range should repeat the check rather than assume it.

The committed runs record `lexichunk_commit` `0346a12` and a local run records none,
because a wheel install carries no VCS metadata. The numbers are identical, which is the
claim that matters.

## What these files do and do not pin

Each `full_benchmark.json` / `structural_benchmark.json` records `lexichunk_version`,
`lexichunk_commit`, `seed`, the models, the documents and the fully resolved run
configuration. Each `evidence_benchmark.json` additionally records a `payload_sha256` and
a `package_tree_sha256` for both LexiChunk and the harness.

Two honest gaps:

- **No harness commit is recorded inside the JSON.** The harness identifies itself by
  version (`1.0.0`) and, for the evidence report, by a content hash of its own package
  tree. The commit above comes from git history, not from the file.
- **The evidence report's `evaluator.package_tree_sha256` and `payload_sha256` no longer
  match a fresh run.** Renaming the package changed the content of the tree the first hash
  covers, and the second covers a payload that names the evaluator. Every metric is
  unaffected — a fresh `make benchmark` reproduces all three strategy aggregates exactly —
  but those hashes fingerprint the code, and the code was renamed.

The run configuration stored in the committed JSON also still names the pre-rename paths
(`src/scaffolder/fixtures/documents`). That is what actually ran, and rewriting it would
falsify the record; the current paths are in `legal-rag-eval.yaml.example`.

## Why the JSON is committed at all

These files are large and machine-generated, which is normally a reason to keep them out
of a repository. They are here because the README makes specific numerical claims and the
only way to check one is to see the run. `.gitattributes` marks them `linguist-generated`
so they do not dominate the repository's language statistics or clutter diffs.
